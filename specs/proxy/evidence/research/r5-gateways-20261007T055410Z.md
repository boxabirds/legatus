# R5: General LLM gateways and L7 proxies vs Legatus v1 proxy (2026-10-07)

Labels: [D] documented (doc/source read), [I] inferred, [U] unverified. Source clones in ./repos (shallow, 2026-10-07).

## Verdict
No candidate does R4 (header-else-body-hash affinity table with idle expiry + load-aware spill) AND R5 (per-backend cap 4 + timed HOLD queue) AND R1 byte-faithful SSE. Closest by mechanism: HAProxy (but GPL-2, body hashing fragile). Closest by feature set: Bifrost (Go, Apache-2.0, plugin hooks, queue-wait) but no affinity and re-serialises. LiteLLM has affinity and hooks but 429s instead of holding and is Python/heavy. Recommendation: build the thin Rust proxy; steal designs (OpenRouter's key derivation, HAProxy's hash-preserve-affinity=maxconn + timeout queue semantics, LiteLLM's key-scoped pin TTL cache).

HAProxy (doc/configuration.txt master)
- R1 YES [I]: L7 proxy forwards bodies and SSE unchanged.
- R3 PARTIAL: map/ACL on model needs body parse (below).
- R4 PARTIAL: header key easy: `balance hdr(<name>)` (line 6639) or `stick on req.hdr(...)` + `stick-table ... expire` = exact table with idle expiry [D]. Body key: `option http-buffer-request`/`http-request wait-for-body` then `req.body,json_query('$.messages[0].content')` and `balance url_param ... check_post` only form-encoded (lines 6616, 10817, 17471, 22540) [D]. Hashing system+first user is possible via set-var then sha1 [I], but body is limited to `tune.bufsize` (default 16384; larger needs `tune.bufsize.large`, lines 4259-4285) and JSON key order is client-defined (tools arrays may precede messages) [I]. Bounded-load: `hash-balance-factor` (>100, 125-200 reasonable, lines 8356-8380) and `hash-preserve-affinity maxconn|maxqueue` which skips saturated servers along the ring and enqueues to the last if all saturated (lines 8395-8410) [D]. Spill is by average-load factor, not an exact table plus spill; combining stick table + spill needs `use-server`/`stick` with fallback [I].
- R5 YES [D]: server `maxconn 4` queues; `timeout queue` bounds wait, then 503 (line 15165-15185). This is the pre-existing hold queue. Caveat: queue per server vs per backend, and a held request that already chose a server by hash waits on that server [I].
- R6 PARTIAL: `option httpchk GET /health`; `agent-check` reads a string that can set `weight:` and `maxconn:` from a sidecar (line 18700+) [D] so /metrics or /api/ps load needs a sidecar [I]. R7 PARTIAL: Prometheus exporter, stats page, log-format; cannot log `cached_tokens` from SSE response body [I]. R8: GPL-2 FAILS permissive [D LICENSE]; binary small, RSS a few MB [I]; macOS supported but a Homebrew build [I]. R9 PARTIAL: Lua/SPOE; per-backend body patch (chat_template_kwargs) is awkward [I]. R10 YES.

nginx OSS: `hash $var consistent` and `max_conns` OK; `queue [timeout]` and cookie/learn stickiness historically commercial (sticky learn open from 1.29.6) [D upstream module doc]. OSS `max_conns` over limit: no hold (error) [I]. Body hashing needs njs/Lua [I]. NO for R5 OSS.

Envoy: ring_hash/maglev hash_policy sources: header, cookie, connection properties, query param, filter state (set via Lua/ext_proc to carry a body hash) [D route_components]. Circuit breakers: pending-request queue exists, overflow fails fast (`upstream_rq_pending_overflow`); no timed hold queue documented [D arch_overview; timeout inferred from route timeout]. Powerful but needs custom ext_proc/Lua for R4 and R5. Heavyweight config; fine as a data plane, not an answer.

Traefik: sticky sessions cookie-based; no header hash, no maxconn queue found; docs fetch failed [U/I]. NO.

vLLM Semantic Router [D local doc 20260917-nadirclaw-vs-semantic-router.md]: Envoy + Go ExtProc + Rust classifiers; strict response schema REJECTS llama-server `timings` and MTPLX extras (MEASURED) -> fails R1/R2; session stickiness only via x-session-id within a decision; images 250 MB + 170 MB, macOS "not qualified" (Colima VM). NO.
NadirClaw: noncommercial licence, drops chat_template_kwargs, forces tool requests to cloud, 372-733 MB RSS [D local doc]. NO.

OpenRouter (reference): conversation key = hash of first system/developer message + first non-system message; override with `session_id` body field or `x-session-id`; sticky 10 minutes idle, errors do not refresh [D openrouter.ai/docs/guides/best-practices/prompt-caching]. This is nearly the R4 spec, a validated design to copy.

## Ranked shortlist
1. Build (Rust) with borrowed designs. R4+R5 are the core and nobody ships them together.
2. HAProxy as an interim/reference only: gets R1, R5, header-keyed R4, health, metrics for ~zero code; fails licence, body-key reliability (16 KB buffer), cached_tokens logging, R9. Usable as a fast spike to validate the maxconn=4 + timeout queue policy on real harnesses.
3. Bifrost as a plugin host: queue-wait + Go plugins could implement R4 as a PreLLMHook; cost is a large codebase, typed re-serialisation (byte-faithful unverified), per-provider (not per-backend) concurrency.
4. LiteLLM: affinity and hooks exist, but 429 on cap, Python RSS in hundreds of MB, re-serialising. Not worth it.

## Gaps after adoption (any candidate)
Body-derived key with expiry table; load-aware spill using engine signals (llama-server /metrics, Ollama /api/ps); hold queue that is global per pool and affinity-aware (a held request should be allowed to spill after a short wait); cached_tokens extraction from streamed final usage chunk for feedback (R7/R9); engine-specific health. All of these are custom code in any adoption path.

## Effort estimate [I]
Build: Rust proxy previously prototyped at 0.06 ms added latency, 3-6 MB RSS; remaining work is table+expiry, queue with timeout, health/metrics scrape, logs: small. Adopt+extend HAProxy: low config effort, high friction on R4-body/R7/R9 and GPL. Bifrost: medium (learn plugin API, verify byte fidelity), 10x+ footprint likely (Go, unmeasured). LiteLLM: low config, big footprint, structural 429 behaviour must be forked.
