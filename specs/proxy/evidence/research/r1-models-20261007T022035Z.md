## Qwen3.8-Flash-Next  (model_type qwen4_exp; "early preview of Qwen4 architecture")
Source: HF card + raw config.json https://huggingface.co/Qwen/Qwen3.8-Flash-Next/raw/main/config.json ; tech report https://arxiv.org/abs/2608.30320 ; blog https://qwen.ai/blog?id=qwen3.8-flash-next (page body did not render for me, so only seen via search snippets)
- MoE, 125B total / 6B active, plus 51B n-gram embedding tables (host-offloadable) and 4B MTP [D, HF card]. 512 experts, 10 routed + 1 shared, moe_intermediate 640 [D config].
- 48 layers = 12 x (3 x Gated DeltaNet->MoE, 1 x Qwen Sparse Attention->MoE): 36 GDN + 12 QSA [D]. hidden 2560.
- GDN: 16 QK heads, 48 V heads, head dim 128, conv kernel 4, ssm dtype float32 [D config].
- QSA layers: 24 Q heads, 2 KV heads, head_dim 256; indexer 4 heads, 1 shared key head, dim 128, compress ratio 4, budget 2048 tokens (512 blocks) [D config/card]. Attention is sparse over a FULL cache: SGLang says "Only 12 of 48 layers store growing attention K/V, while the other 36 GDN layers use fixed-size state" and "QSA adds one BF16 compressed index key per four tokens" https://www.lmsys.org/blog/2026-08-26-qwen-flash-next/ [D].
- Context 262,144 native, extensible to 1,000,000 [D card]. 1 MTP layer (full attention, own KV).
- KV bytes/token, full-attn layers (f16/bf16): 12 x 2(K,V) x 2 x 256 x 2 B = 24,576 B = 24 KiB/token [I]. 128k = 3 GiB, 262k = 6 GiB. Indexer adds ~12 x 256 B/4 = ~768 B/token [I]. MTP layer adds 2 KiB/token (owner's profiles.tsv figure, consistent with 1 layer) [I].
- Caveat: owner's profiles.tsv cites a Strix Halo report of ~5 GB for 128k->256k (about 38 KiB/token), above my 24 KiB. Unreconciled; the llama.cpp qwen4exp branch may allocate differently. [U]
- Recurrent state per sequence: 36 layers x 48 x 128 x 128 x 4 B (fp32) = 108 MiB, plus conv state (10,240 ch x 3 x 36) ~2-4 MiB => ~110-115 MiB [I]. Constant in context length.
- Authors on caching/concurrency: HF card does not mention prefix caching or concurrency [D, absence]; it recommends SGLang/KTransformers/vLLM for production. SGLang post: compressed cache "follows Radix Cache ownership" with page-aligned full_slot/4 addressing; offloading n-gram embeddings raised KV capacity 1.84M -> 3.28M tokens per GPU [D]. Qwen3.8 tech report abstract has no cache-size or prefix-cache statements [D, absence]. Radix-style prefix caching therefore exists in SGLang for this model; I did not read how the GDN state is checkpointed there [U].

## Qwen3.8-27B (config says model_type qwen3_5; same architecture class as Qwen3.5/3.6 27B)
Source: https://huggingface.co/Qwen/Qwen3.8-27B and raw config.json
- Dense, 27B, hidden 5120, FFN 17408, vocab 248,320, vision encoder (27 layers) [D].
- 64 layers = 16 x (3 x Gated DeltaNet->FFN, 1 x Gated Attention->FFN): 48 GDN + 16 full attention [D, layer_types list]. Plus 1 MTP layer (owner's discovery.md counts 65 layers, 16 with KV; llama.cpp metadata head_count_kv 4).
- Full attention: 24 Q, 4 KV heads, head_dim 256, partial rotary 0.25. GDN: 16 QK / 48 V heads, dim 128, conv 4, ssm fp32 [D].
- Context 262,144 native, extensible to ~1M [D].
- KV: 16 x 2 x 4 x 256 = 32,768 elements/token = 64 KiB/token at f16 [D in owner's docs/discovery.md line 38, matches config; I]. 128k = 8 GiB, 262k = 16 GiB. q4_0/q8_0 scale roughly by 0.28/0.53 [I].
- Recurrent state per sequence: 48 x 48 x 128 x 128 x 4 B = 144 MiB fp32, plus conv ~3-6 MiB => ~150 MiB [I].
- Authors on caching/concurrency: card says nothing about prefix caching or concurrency [D, absence]. MTP trained multi-step.

## Why this matters for affinity (the implication, mostly [I])
- Prefix reuse on both models is NOT like a pure transformer. KV rows can be truncated at any token, but the GDN state (110-150 MiB) cannot be rolled back; reuse is only valid at a saved state snapshot. llama.cpp does this with --ctx-checkpoints (owner's config uses 8; comment: "without saved checkpoints a returning agent turn re-reads its whole prompt") [D owner config]. Tail-Replay paper describes the general problem: https://arxiv.org/abs/2608.30310 [D].
- So per-session cache cost on a node = KV (24-64 KiB/token) + checkpoints (up to N x ~110-150 MiB) + 1 live state. A session at 64k tokens on 27B ~ 4 GiB KV + ~150 MiB/checkpoint. Affinity pays: a request landing on another node loses all checkpoints and does a full prefill, which the owner measured as brutal on Strix Halo llama.cpp (172-351 tok/s; 6-8 min compaction re-reads) and cheap elsewhere (4090 ~2,000 tok/s).
- llama.cpp hybrid-cache bugs to know: ggml-org/llama.cpp#29092 (ROCm GDN state carried across requests on reused slot) https://github.com/ggml-org/llama.cpp/issues/29092 ; Bonsai-demo #147 cached_tokens:0 (different model) cited in owner's bonsai2 note.
- Owner's bonsai2 note (docs/research/20260918-bonsai2-concurrent-sessions.md) is about Bonsai 2 27B (a different, PrismML model), not Qwen3.8; its premise (warm sessions prefill only the delta; -np N batches decode) was unmeasured. Owner's measured MTP result: net loss (0.81-0.87x) at 8 concurrent on Strix Halo; gufo 8-user mixed MTP 106 vs llama.cpp 62 tok/s (gufo BENCHMARKS.md).
