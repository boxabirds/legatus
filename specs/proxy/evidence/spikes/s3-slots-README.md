# Spike 3: do `slots` match real engine concurrency? (round 2)

Versions: Ollama 0.35.1 frozen (latest not checked; frozen on purpose), llama-server brew 0.5.0 b11146 (v0.6.0 exists, not used), mlx_lm 0.32.0, node 25.2.1, model qwen3:1.7b (Q4_K_M GGUF blob / mlx-community Qwen3-1.7B-4bit). All numbers are from a REAL model. Machine: M2 16 GB, shared with other agents and a 65%-CPU `dbench` process: absolute tok/s drift 2x between identical runs (llama N=1 14 to 34 tok/s). Trust ratios and shapes, not absolutes.

## Data paths (never overwritten; see "Honesty note")
- `runs/run-20261006T223314Z-preruleset-archive/{logs,results}/`: main matrix (N 1,2,4,8 x3 reps, ~600-token prompt, 64 out) for ollama-{default,np2,np4}, llama-{default,np1,np2,np4,np4-c32k}, mlx-default, long-prompt N=2 (~6850 tokens) files `*-long.json`, decode-bound variant and long N=1 for llama-{np1,default,np2} and mlx (`*-decode.json`, `*-long1.json`).
- `runs/run-20261006T22*-<tag>-extra/`: later runs with ENV.txt (command, versions, load), server.log, decode/long1 results: ollama default/np2/np4, llama np4.

## Findings (VERIFIED unless noted)
1. Ollama 0.35.1 default `OLLAMA_NUM_PARALLEL` is 1 (server config line), runner is its own llama-server `-np 1`. Setting 2 or 4 gives `-np N` and `-c ctx*N` (n_ctx_slot unchanged 8192). /api/ps reports size_vram growing with parallel: 2.36 GB (1), 3.36 GB (2), 5.33 GB (4), but no slot or queue field. No load signal during runs (psChange only expires_at). Response headers carry nothing useful (content-type, date, transfer-encoding).
2. Ollama queue: extra requests get NO headers until service starts (hdr == TTFT, e.g. N=8 default: hdr 2.8 s to 39.9 s), no errors up to N=8 (OLLAMA_MAX_QUEUE 512, not tested).
3. llama-server: `/props total_slots` equals what runs (default 4, np1/2/4 as set). Default (auto) gives 4 slots with kv_unified=true (each slot may use the whole -c); explicit `--parallel N` gives kv_unified=false and splits -c: `-c 16384 -np 4` = 4096 per slot, and our 6850-token prompt got 400 `exceed_context_size_error` (np4 long, file `llama-np4-long.json`); `-c 32768 -np 4` works. Queued requests get headers EARLY (hdr 40 to 120 ms even when queued, `rd` deferred counted) but no tokens until a slot frees. `/metrics` (needs `--metrics`) `requests_processing` and `requests_deferred`, and `/slots` `is_processing` count, were exact in every run (rp = min(N,slots), rd = N - slots). `/props` is static (no load). `/slots` wakes a sleeping server (round 1, s7 `llama-E-wake-endpoints.log`, cited, not redone); /metrics, /health, /props do not.
4. mlx_lm.server 0.32.0: no /props /metrics /slots (404), no load signal. It batches: overlap == N up to 8 (defaults decode-concurrency 32, prompt-concurrency 8; code `server.py` batches unless draft model, seed given, kv-bits set or cache not mergeable). Headers sent at once (10 to 40 ms). But batching buys nothing: decode-bound aggregate 55, 58, 53, 51 tok/s for N 1,2,4,8 (per-request speed 59, 31, 14, 7): time-slicing, not a speedup. Round-1 "batched completion with 1 default slot" is settled: it IS concurrent, it is NOT more capacity.
5. Throughput scaling is small everywhere. Prefill-bound workload (600-token prompt, 64 out), aggregate tok/s N=1/2/4/8: ollama default 32/27/16/12; ollama np2 18/19/18/18; ollama np4 15/18/23/22; llama np1 15/15/14/14; llama np2 15/19/18/18; llama np4 14/16/21/19; llama default 16/15/19/20; mlx 29/21/20/21. Decode-bound (20-token prompt, 128 out) N=1/2/4/8: llama np4 28/34/46/49; llama default 23/33/39/44; ollama np4 27/33/43/49; llama np2 24/28/29/32; ollama np2 31/35/37/34; llama np1 34/25/27/25; ollama default 49/27/24/25; mlx 55/58/53/51. Max real gain about 1.6-1.8x at N=4 on decode-bound traffic with 4 slots, about 1.3x on prefill-bound, and it stops at the slot count (overlap = slots for Ollama and llama-server; N beyond slots only queues).
6. TTFT inflation per extra request (~600-token prompt): parallel slots share prefill, so every request in the batch gets TTFT about N x single (llama np4: 2.3 s, 3.5 s, 7.4 s for N 1,2,4; mlx 1.1, 3.5, 7.4, 15.9 s; Ollama np4 2.3, 3.5, 6.4). Serial engines (np1) keep the first request's TTFT and queue the rest (llama np1 N=8: ttft 2.3 s to 33.8 s).
7. LONG prompt (~6850 tokens), N=2, TTFT of the two requests: llama np1 25.5/54.8 s (serial); llama np2 60.7/61.0 s; llama default 58.3/58.5; llama np4 -c32k 60.4/60.7; ollama default 27.7/59.2 (earlier long1 baseline 19.3 to 23.8 s); ollama np2 33.2/49.7; ollama np4 40.1/58.5; mlx 56.5/56.5 (single 25.6). Prefill is ONE shared compute pool (~250-270 tok/s here): a second long prompt delays the first one by up to 2x with parallel slots and gains nothing overall. Per-request decode drops (np1 28 tok/s vs np2 10).
8. Observed useful concurrency (smallest N reaching 90% of best aggregate), decode-bound / prefill-bound: ollama default 1/1; ollama np2 2 (flat after)/2; ollama np4 4/4; llama np1 1/1; llama np2 2/2; llama np4 4/4; llama default 4/4; mlx 1/1 by throughput (while overlap reaches 8).
9. One `fetch failed` at 5 ms in llama np4 N=2 rep 1: client reusing a connection the server had closed (llama keep-alive timeout 5 s). Client artifact, not capacity; Legatus' router must retry-on-stale-connection or disable keep-alive reuse for llama.

## RECOMMENDED effectiveSlots (story 4)
Declared slots is only a ceiling and measured concurrency should lower it, never raise it (consistent with story 59 TC-68). Per engine:
- Ollama: default 1. If the owner sets NUM_PARALLEL=n, the registry `slots` must equal n (there is no discovery: `/api/ps` has none; the router cannot read the env). Cap measured. Do NOT trust declared 4 without a measured knee.
- llama-server: do NOT hardcode 4. Read `/props total_slots` (exact) as declared, cap at measured useful (observed equal to total_slots on decode-bound traffic). Also read per-slot `n_ctx` (`/slots n_ctx`) as the context the node honours (story 11).
- mlx_lm: default 1 stays right as a capacity number even though 8 requests run concurrently: aggregate does not grow, per-request speed divides by N. Slots above 1 would only add latency.

## Design consequences (exact changes)
- Story 4: replace `ENGINE_DEFAULT_SLOTS llama-server 4` by "total_slots from the node's `/props` discovered at registration; 4 only as fallback labelled declared_unverified". TC-284 expectation changes accordingly. Add node field `slots_source: registry|props|default`. Keep `min(declared, measured.concurrencyUseful)`.
- Story 11: effective context per request on llama-server and Ollama is per-slot (`c/np`; Ollama keeps per-slot ctx, total ctx grows), so the context filter must use per-slot ctx, not the total `-c`; a node configured `-np 4 -c 16384` refuses 6850-token prompts (400) though `-c` says 16384.
- Story 24: the slot ledger is correct for llama-server and Ollama (overlap == slots; beyond that requests queue, never error) and the lease protects fairness of TTFT, not throughput; TC-106 expectation should be rewritten: refusal at slots+1 is right; real concurrency never exceeded slots; mlx is the exception (no cap, 8 concurrent): the only protection is the router's lease count. Note a queued request on Ollama has no headers: a pi/agent timeout there would fire before service.
- Story 13: `/slots` + `/metrics` give busy and deferred exactly for llama-server (poll `/metrics` only, `/slots` wakes a sleeping server); Ollama and mlx_lm give nothing: the router's own in-flight counter is the only signal there. Information only, as designed.
- Story 59: knee by the probe's "aggregate within 90% of best" would pick wrong values on prefill-bound probes (prefill-bound gains are only 1.1-1.5x, within the 2x run-to-run noise seen here). Concurrency curve must use a DECODE-bound probe (short prompt, ~128 out) and also record per-request speed; keep CALIBRATION_KNEE_FRACTION on per-request speed carefully: at the real optimum (N=4, np4) per-request speed is 0.45 of N=1, so a fraction above 0.5 picks 1-2. Pick knee by aggregate gain (>=1.15x per doubling) not per-request speed. Add a long-prompt N=2 probe result `prefill_contention_ratio` (first TTFT with a second prompt / alone: 2.1-2.4 here) to the profile.
