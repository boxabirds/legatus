# R2: vLLM prefix caching, hybrid (GDN/Mamba) models, saturation, cache-aware routing

Date: 2026-10-07. Labels: [D] documented in a primary source I fetched; [I] inferred by me; [U] unverified / only seen via search snippet or a summarizer I could not cross-check.
Caveat: WebFetch returns model-summarized pages, not raw text; quotes are as returned. Latest vLLM release seen: v0.31.0 (5 Oct 2026); v0.30.0 (22 Sep); v0.29.0 (9 Sep).

## 1. Dense models: automatic prefix caching (APC)

- [D] Block hashing: each KV block is hashed from the tokens in the block plus the hash of the parent (prefix) block, plus extras (LoRA id, image hashes). https://docs.vllm.ai/en/latest/design/prefix_caching/
- [D] Eviction: LRU over free blocks (free queue; head evicted first). Blocks of a finished request are freed in reverse order so the tail block (least reusable) is evicted first. Cached blocks stay in the pool until their memory is needed. Same URL.
- [D] APC only cuts prefill time, not decode. https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/
- [D] "Concurrency" = max_num_seqs (max sequences per scheduler step/running batch) and max_num_batched_tokens (token budget per step); the waiting queue is consulted only while budget and running-queue size allow (search snippet of scheduler docs/ Gangmuk Lim blog; [D]/[U] mix). Under FCFS even a high-priority waiting request cannot preempt running ones (issue #40004 snippet).
- [D] Preemption: when KV cache runs out, running requests are preempted and recomputed later; V1 default is RECOMPUTE, not SWAP. Mitigations: raise gpu_memory_utilization, lower max_num_seqs / max_num_batched_tokens. https://docs.vllm.ai/en/latest/configuration/optimization/
- [I] A preempted request's blocks are freed but remain hash-cached until overwritten, so recompute may partly hit the cache; not stated explicitly in the docs I read.
- [D] Monitoring: num_requests_waiting / num_requests_running metrics (older stats-endpoint snippet; Prometheus equivalents exist, [U] exact current names).

## 2. Hybrid models (full attention + Mamba/GDN linear attention)

Mechanism
- [D] Hybrid KV cache manager groups layers into KV cache groups by attention type; different block counts per group. Mamba state is per-sequence O(1) and is padded into attention-sized pages by enlarging the attention block_size until block_size*kv_hidden >= state_size ("can lead to more than 400 block_size"). Prefix hit = intersection of per-group hits. Design doc still says Mamba prefix caching "work in progress", "early stage" (doc may be stale). https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/
- [D] Consequence for chat: block size is large. Qwen3.5 attention block = 528 tokens; Issue #40696: prompts under 528 get ~0% hit (479 tok: ~0%; 552: 95.4%; 979: 53.7%). https://github.com/vllm-project/vllm/issues/40696
- [D] Issue #45238: block sizes grow with model size (528 -> 2096 tokens across Qwen3.5 lineup). https://github.com/vllm-project/vllm/issues/45238

Modes (--mamba-cache-mode)
- [D] `align`: state stored only on the Mamba block grid; a hit can resume only at a block boundary. Per request only the Mamba checkpoint at the LAST block boundary before the prompt ends is retained (null blocks earlier). This is the only mode that works for Qwen3.5-family GDN (issue #45238 text) and is what the LMCache Qwen3.8-Flash-Next recipe mandates ("all not supported").
- [D] Turning on prefix caching for a hybrid model forces align mode (issue #60008, main at 2 Oct 2026). Tracking issue #26201 lists "enable align-mode caching by default for hybrid models" as pending; release-note search snippet says "prefix caching is on by default for hybrid Mamba models" ([U] conflict; treat default as version dependent, set `--enable-prefix-caching` explicitly).
- [D] `all`: checkpoint every block. PR #26807 (GDN all-mode, 126 commits) was OPEN as of the fetch, late July 2026; PR #36649 closed 5 May 2026 in favor of it; PR #50172 (Qwen3-Next all-mode + MTP) OPEN, Sept 2026, scoped to Qwen3-Next only, needs Triton/FLA prefill. v0.30.0 release notes list "the `all` Mamba cache mode deprecated" ([D] via summarizer of the releases page; [U] whether that means removed). Net: for Qwen3-Next/3.5/3.8 treat `all` as not available in a released build. [U] precisely which release first shipped `align` (Mamba2 APC base PR #25752 Oct 2025 tracking; GDN via #30877 per tracking issue; I did not confirm release numbers). 
- [D] PR #26807 testers found align 1.03-1.37x higher throughput than all; bf16 truncation makes cold vs warm outputs differ slightly. LMCache also says cached vs fresh generation is not bit-exact.
- [D] v0.29.0: Mamba prefix caching "9%-25% TTFT improvement" via internal prefill checkpoints; `prefix_cache_retention_interval` CLI arg (default 0); dense retention auto-restored for hybrid + EAGLE/MTP. v0.31.0: flag renamed `--enable-mamba-shared-prefix-checkpoint`; requires align + EAGLE/MTP + `--prefix-match-unit` < block size (docs suggest 64). Off by default. https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/ and https://github.com/vllm-project/vllm/releases

Known limitations / open bugs (all [D] from issue pages unless noted)
- #45238 (open): if the single align checkpoint lands in request-unique tokens, Mamba group misses, the coordinator intersects, and ALL reuse including matching attention blocks drops to 0%, silently. Repro: 1600 shared/600 unique -> 52/64 hits (433 ms TTFT); 1500/700 -> 0% (905 ms). Proposed: K checkpoints per request (2-8 MiB each), fixed global positions, or counters. Directly relevant to multi-turn chat where each turn appends new tokens (the previous turn's end-of-prompt checkpoint is the reusable point; [I] a follow-up turn extends the previous prompt+answer, so reuse depends on the prior checkpoint being a prefix of the new prompt, which it is only if the previous turn's prompt tokenization is a strict prefix and generated tokens are not needed; the answer tokens after the last checkpoint must be re-prefilled).
- #60008 (open, 2 Oct 2026): on Nemotron-3.5-Lightning, align mode costs 13-16% output throughput even with zero hits (eager kernels outside CUDA graphs, prefills split at block boundaries).
- #51250 (open, vLLM 0.26.0, Aug 2026): zero hits on Qwen3.5-35B-A3B, silent no-op. Reporter unsure of main branch.
- #47861 / #53912 (snippets): prefix cache + MTP corrupted outputs on hybrid models in v0.28.0; #47861 fix. [U] merged status.
- #59826 (open): Mamba tail-save/Mooncake and EAGLE resend-cap fixes; Kimi K3 c=128 hit rate 90.5 -> 94.0%.
- Other: #58894 spec-decode acceptance collapse after cache hits (DFlash2, Qwen3.5) [U].
- Qwen3-Next recipe (vLLM recipes site) simply uses `--enable-prefix-caching`; says `--no-enable-prefix-caching` on AMD MI3xx. No concurrency guidance. https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3-Next.html

## 3. The (N+1)th session at a saturated server

- [D] Running slots: bounded by max_num_seqs. Extra requests wait in the scheduler waiting queue (FCFS default; priority policy exists). Nothing is evicted from the running batch merely because a new one arrives.
- [D] KV memory exhaustion is separate: running requests get preempted (recompute) in V1.
- [D] Prefix cache is opportunistic: cached blocks of finished sessions are free blocks and are LRU-evicted when new requests need memory. So with more sessions' working sets than free KV memory, older sessions' prefixes vanish. llm-d measured: at 73% total cache demand vs cluster capacity, cache-blind scheduling produced growing waiting queues and mean TTFT 45-47 s vs 0.3 s for precise-prefix routing (8 pods/16 H100; vendor benchmark). https://llm-d.ai/blog/kvcache-wins-you-can-see
- [I] Hybrid models: each running sequence needs a Mamba state slot plus checkpoints; because only 1-2 tail checkpoints per request are kept in align mode, idle-session retention is cheap per session but the hit granularity is a 400-2000-token block, and hit/miss is all-or-nothing per #45238. The vLLM docs do not publish a hit-rate-vs-session-count curve for hybrids [U].
- [I] "Efficient at ~4 concurrent sessions" is a throughput property, not a cache-retention property; warm sessions that are idle consume no max_num_seqs slot but compete for KV blocks.

## 4. Routing, affinity, offload

production-stack (vLLM project)
- [D] Router logics: roundrobin, session, kvaware, prefixaware, disaggregated_prefill. SessionRouter routes by a configurable session-key header; with no key it picks lowest-QPS server. KvawareRouter routes to engine holding longest prefix match (via LMCache controller), round-robin fallback. https://docs.vllm.ai/projects/production-stack/en/vllm-stack-0.1.4/dev_guide/dev_api/router-logic.html
- [D/U] Prefixaware = hash trie over request text; approximate: tracks requests, not real KV, not eviction-aware (assumes seen prefixes stay cached) -- from a search-result summary, not the primary source; minimum match length falls back to QPS (PR #1089 changes fallback to least-inflight). Verify in source: https://github.com/vllm-project/production-stack/blob/main/src/vllm_router/README.md
- [D] 2026 roadmap lists router-side queuing, prefix-aware, KV-aware as items (issue #855), i.e. not mature. 

llm-d
- [D] Inference scheduler scores pods on prefix-cache affinity plus load (queue length, KV utilization). Two modes: approximate (router-side index of past routing) and precise (consumes vLLM KV-Events for actual block state). Benchmarks: precise 0.30 s mean TTFT vs approximate 13.3 s vs load-only 47 s vs random 45 s. Session-based affinity "misses cross-user cache opportunities". https://llm-d.ai/blog/kvcache-wins-you-can-see , https://developers.redhat.com/articles/2025/10/07/master-kv-cache-aware-routing-llm-d-efficient-ai-inference
- [U] Whether KV-Events/precise mode work for hybrid Mamba groups: not documented in what I read. Kubernetes-centric; heavy for 5 machines.

Offload
- [D] vLLM OffloadingConnector (blog 2026-01-08): completed GPU blocks copied async to pinned CPU memory; CPU tier LRU (arc optional); CUDA/ROCm/XPU only (so not Apple/Metal). Docs do not mention hybrid models. https://docs.vllm.ai/en/stable/features/kv_offloading_usage/ , https://vllm.ai/blog/2026-01-08-kv-offloading-connector. Issue #60004: OffloadingConnector wrong output on CPU hits with a hybrid-ish ("LHBNC") config [U details].
- [D] LMCache MP connector supports hybrid via KV cache groups; Mamba hybrids need `--separate-object-groups`, align mode, matched chunk/block size, not bit-exact, no CacheBlend/CacheGen. https://docs.lmcache.ai/mp/hybrid_models.html , https://docs.lmcache.ai/recipes/qwen3_8_flash_next.html
- [D] llm-d filesystem offload backend does no eviction/cleanup; CPU and shared-storage tiers independent (v0.7 doc; latest llm-d is v0.10).

## 5. What this means for a cache-affine proxy

See the summary in the chat report. Short form: vLLM gives no session-pinning primitive; affinity must live in the proxy. Hybrid caching is coarse (block 400-2000 tokens), all-or-nothing, one checkpoint near the prompt tail, and vulnerable to silent 0% hits (#45238), so the proxy should keep conversations byte-stable (identical prefix tokens, no re-templating/system-prompt drift), pin by session id, and measure real hit rate from each node's /metrics (prefix_cache hits/queries) rather than assuming warmth. The proxy must budget slots (max_num_seqs) and treat KV memory as the real constraint.
