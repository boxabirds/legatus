# R6: inference-aware routers and local-LLM balancers (2026-10-07)

Labels: [D] documented (doc or code read), [I] inferred from code, [U] unverified. Repos cloned and read at HEAD on 2026-10-07 (gh api for licence/release).

## Headline
No project meets R1-R5 together. The closest is **Olla** (Go, Apache-2.0): Anthropic + OpenAI passthrough, sticky sessions keyed by header else body-prefix hash, idle TTL, llama.cpp/Ollama/vLLM/SGLang/mlx profiles, dashboard. It has NO admission cap or hold queue and NO load-aware spill. Those two (R5 and half of R4) are the real build. SMG and vLLM router have the best queue/spill design but assume SGLang/vLLM engines.

## Per project
**Olla** (thushan/olla; Go; Apache-2.0; v0.0.29 2026-08-10, pushed 2026-09-27; ~315 stars, one dominant author, 100+ commits since Aug 1). Single binary, YAML.
- R1 YES [D]: /v1/messages passthrough "for backends with native support", translation otherwise (docs/content/api-reference/anthropic.md l.18-20). Byte-faithfulness of SSE not audited [U].
- R2 YES [D]: profiles for llamacpp, ollama, vllm, vllm-mlx, sglang, omlx, lmstudio, openai-compatible (config/profiles/). No mlx_lm.server or gufo profile by name; generic openai-compatible would cover [I].
- R3 PARTIAL [D]: model discovery unifies models across endpoints; pool = endpoints that serve the model. No explicit alias-to-pool config seen.
- R4 PARTIAL [D]: internal/adapter/balancer/sticky.go. Key order session_header (X-Olla-Session-ID), prefix_hash (FNV-64a of first 512 bytes of the `messages` JSON), auth_header, ip. ttlcache sliding idle TTL (default 600 s), LRU cap 10000, exact key->URL table. Gaps: (a) Select() returns the pinned endpoint whenever it is routable, so NO load-aware spill (sticky.go l.90-118); (b) the hash covers `messages` only: for OpenAI bodies the leading system prompt dominates the first 512 bytes, so different conversations from one harness collide [I]; Anthropic `system` is outside `messages`, so that case is better [I]; (c) it cannot tell a title/side request from the main session.
- R5 NO [D]: only per-minute rate limits (config.yaml l.37) and retry on connection failure; no per-backend running cap or hold queue found in internal/.
- R6 PARTIAL [D]: health checks with circuit breakers; llamacpp profile lists /health, /props, /slots, /metrics but they are commented out/disabled (config/profiles/llamacpp.yaml l.52-64). Slot/load signals not used for routing [I].
- R7 PARTIAL [D]: read-only dashboard /internal/ui/, /internal/metrics, X-Olla-* response headers incl. sticky hit/miss/repin. cached_tokens appears only in the Anthropic translator streaming code [I]; no per-request cached_tokens log [U].
- R8 YES. R9 PARTIAL: clean Go EndpointSelector decorator pattern (StickySessionWrapper wraps any selector), so a fork can add spill/admission; converter/translator packages exist. R10 YES (retry configurable, can disable).

**SGLang Model Gateway (smg)** (sgl-project/sglang/sgl-model-gateway; Rust; Apache-2.0; sglang v0.5.21 2026-10-02, gateway commit 2026-10-06).
- R1 PARTIAL: OpenAI chat/completions/responses yes; no inbound /v1/messages (grep: "anthropic" only as upstream auth in header_utils.rs) [D].
- R2/R3 PARTIAL: local-worker registration probes SGLang endpoints (/server_info, /model_info; core/steps/worker/local/discover_metadata.rs). Non-SGLang servers go through the "External"/OpenAI router (routers/openai/router.rs); its select_worker_for_model uses find_best_worker_for_model, no policy call seen, so cache_aware likely does NOT apply to llama-server [I]. Kubernetes optional [D].
- R4 PARTIAL: policies cache_aware (approximate radix tree of request text plus shortest-queue spill past balance_abs/rel thresholds, cache_aware.rs), consistent_hashing and `manual` (X-SMG-Routing-Key sticky table, max 2 candidates, remap only on unhealthy; manual.rs) [D]. Tree is router-side guess, no engine feedback [I]. Needs SGLang workers for full value.
- R5 PARTIAL: token bucket `--max-concurrent-requests` is GLOBAL, with --queue-size and --queue-timeout-secs FIFO (README l.732). Not per-backend [D].
- R6 NO for llama.cpp (SGLang loads only). R7 PARTIAL: 40+ Prometheus metrics, OTel; no dashboard [D]. R8 NO-ish: Rust, big, SGLang-shaped. R9 PARTIAL (WASM middleware, policy trait). R10 n/a.

**vLLM Router / production-stack** (vllm-project/router: Rust SMG fork, Apache-2.0, pushed 2026-10-02, no releases; vllm-project/production-stack: Python, Apache-2.0, chart 0.1.13 2026-09-29).
- Python router: has /v1/messages (main_router.py l.298), static backends allowed, session routing = uhashring consistent-hash ring on a configurable header or body field, NOT an exact table, no idle expiry; kvaware needs LMCache controller; loadaware exists; scrapes vLLM /metrics [D]. Assumes vLLM only. R5 NO, R6 vLLM only.
- Rust router: cache-aware, consistent hash, plus opt-in "Program scheduling" (docs/program_scheduling.md): program identity from headers (Claude Code, Codex/OpenCode, x-session-id with `auto`), a RequestPool that HOLDS requests when a backend lacks logical capacity, KV-protecting resume order. Closest design match to R4+R5, but capacity model is token-based, calibrated for vLLM, observations via VllmMetricsObservationProvider [D]. Useful as a design reference, not adoptable for llama.cpp.

**llm-d / Gateway API Inference Extension** (Apache-2.0; llm-d v0.10.0 2026-09-29; GIE v1.6.2 2026-09-17). Kubernetes + Envoy ext_proc, InferencePool CRDs, vLLM/SGLang model-server protocol (queue depth, KV usage metrics). NO for R8 and R2; a "standalone" EPP chart was mentioned in search results [U]. Reference for scorer design only.

**Paddler** (distantmagic/intentee; Rust; Apache-2.0; v4.1.0 2026-07-19, active). v4 is a platform with its own embedded llama.cpp "agents" ("built-in llama.cpp engine ... its own implementation of llama.cpp slots", README). Not a proxy to external llama-server/Ollama/mlx [D]. Slots: agent-reported slots_total/slots_processing; dispatch = least busy with capacity (agent_controller_pool.rs). Queue: YES, BufferedRequestManager holds requests with a timeout and max_buffered_requests (buffered_request_manager.rs l.19-75), the best R5 implementation I found, but tied to its agents. Affinity: NO (grep for affinity/sticky: none). Anthropic: NO (only /v1/chat/completions in compatibility/openai_service). Dashboard: YES. Verdict: R5 pattern to copy, not adopt.

**llama-swap** (mostlygeek; Go; MIT; v262 2026-10-03, very active, ~5.9k stars). R1 YES (/v1/messages in server.go l.136; OpenAI). R2 PARTIAL (it launches/swaps local processes; `peers` proxy to remote /v1 servers). R3 NO for pools: peer model is addressed `peer/model`; unqualified accepted only if exactly one peer provides it (docs/config.example.yaml l.789-796). R4 NO. R5 NO: concurrencyLimit returns 429 immediately, "rather than queued" (internal/server/concurrency.go). UI+Prometheus yes. Good single-node front-end, not a pool balancer.

**Ollama** (MIT; v0.40.0 2026-09-25): single-node scheduler; OLLAMA_NUM_PARALLEL (default 1), OLLAMA_MAX_QUEUE 512, MAX_LOADED_MODELS, KEEP_ALIVE (envconfig/config.go l.277-281); /v1/messages and /api/ps exist (routes.go l.2327, 2348). No cross-host balancing. It is a backend, not a router.

**LocalAI** (MIT; v4.11.0): federated mode routes each request to one worker "based on the load balancer's decision", algorithm unspecified, no affinity/queue documented [D, localai.io/docs/features/distribute]. Needs P2P token, single model limitation. NO. **GPUStack** (Apache-2.0; v2.2.3): GPU cluster manager for vLLM/SGLang/TRT-LLM; affinity/queue not documented in the overview [U]. NO. **exo** (Apache-2.0; v1.0.71 2026-04-23): shards one model across devices over MLX; has OpenAI/Claude Messages/Ollama APIs; not a request balancer [D].

## Small new projects (all young, mostly single author)
- JochenLinnemann/llamacpp-affinity-proxy (Go, MIT, created 2026-09-16, impl still under PR review): header to llama-server `id_slot` injection, one backend only [D]. Idea worth stealing (slot pinning via id_slot).
- utopiafallen/proxycache (Go, no licence file seen, 2026-09): llama.cpp only; tokenizes per backend, scans /slots and disk KV, routes cache hits while queue < limit (default 2), per-backend queue max 5, migrates waiting requests after 120 s, P2P KV transfer. Best conceptual fit for "cache-hit feedback + spill + hold", but OpenAI only, unlicensed [D].
- AutreMachine/llm-router (Python, no licence, 2026-10-05): per-machine `max_concurrent` slots, priority hold queue with queue_timeout (503), model->machines, dashboard; no affinity, OpenAI only [D].
- issixx/llama-balancer (Python/Flask, MIT, 2025-11): sticky 3 min by client IP, per-server request-max, regex model routing; Windows-oriented [D].
- FBR65/loadbalancer (Python, MIT, 2026-09-28): least-loaded from llama.cpp/vLLM /metrics, no affinity [D].
- geeks-accelerator/ollama-herd (Python, MIT, 23 stars): Ollama/MLX fleets, mDNS, scored routing incl. "affinity", queues, dashboard [D]; Anthropic and llama-server support not confirmed [U].
- akiojin/llmlb (Rust, MIT, 10 stars): OpenAI + Anthropic /v1/messages inbound, endpoint scheduler, cloud prefixes; affinity not found [U].
HN: "Show HN: Open-source load balancer for llama.cpp" (item 40550059) is the original Paddler.
Owner's awesome-local-ai docs: no router evaluation; relevant facts only: hybrid combos run `-np 1`, so any side request (titles) evicts the main KV (docs/research/20260917-nadirclaw-vs-semantic-router.md l.361-374); llama-server emits `timings` per slot (l.149). This argues for keying affinity per conversation AND capping to 1 concurrent per slot on those nodes.

## Ranked shortlist
1. **Olla, forked/extended** (Go). Covers R1, R2, R3 (mostly), R8, and half of R4 and R7 today.
2. **Build a thin proxy in Go/Rust, borrowing designs**: proxycache (hit-aware routing, queue migration), Paddler (hold queue + timeout), SMG cache_aware (load-imbalance spill thresholds), Olla (key order, sticky wrapper).
3. llama-swap in front of nodes only as a per-node process manager, not as the router.
4. SMG/vLLM router: reject. Wrong engine assumptions, global rather than per-backend admission, no inbound Messages (SMG).

## Remaining gaps if adopting Olla
- R5: per-backend running counter plus hold queue with timeout (the counting hooks Increment/DecrementConnections already exist on the selector interface, sticky.go l.78-88) [I].
- R4: load-aware spill when pinned backend is full, key choice that avoids system-prompt collisions (hash the first user turn, or skip system), exact-table expiry semantics check.
- R6: enable and consume /slots, /metrics, /props, /api/ps for load.
- R7: per-request cached_tokens log (parse usage from SSE tail) and cache-hit feedback to affinity.
- R1: verify SSE byte-faithfulness and that cache-affecting fields are untouched.
- Sole-maintainer risk (bus factor 1, v0.0.x, pre-1.0).

## Adopt-and-extend vs build
Adopt Olla and extend: roughly 1-2 weeks of Go for admission + spill + signals + logging, inheriting 11 backend profiles, Messages translation, dashboard; cost is a v0.0.x single-maintainer base and Go. Build from scratch: ~3-5 weeks to reach parity on R1/R2/R7 (Messages passthrough, profiles, dashboard) before the novel parts. Recommendation: spike Olla for two days against real harness traffic (pi, Claude Code) checking SSE fidelity and sticky behaviour; if it passes, extend; otherwise build thin. Effort figures are my estimates [I].
