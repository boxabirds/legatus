# R3: SGLang prefix cache, routers, sticky routing practice (research date 2026-10-07)

Labels: [D] documented in a fetched primary source, [I] inferred by me, [U] unverified / not found. Fetched pages are summarized by a small model (WebFetch), so exact numbers should be re-checked against the source before they go into a spec.

## 1. SGLang single-node behavior

### RadixAttention / eviction
- Radix eviction policy flag `--radix-eviction-policy`: lru (default), lfu, slru, priority. [D] https://docs.sglang.io/advanced_features/server_arguments.html
- Hybrid models use two LRU lists (Mamba state timestamps and KV timestamps separately). KV must be evicted leaf-to-root; Mamba states can be evicted from any node. [D] PyTorch blog, last updated 2025-12-03: https://pytorch.org/blog/hybrid-models-meet-sglang-more-than-full-attention/
- Newer "Unified Radix Cache" (LMSYS blog 2026-08-11): one token-keyed tree, FULL / SWA / MAMBA components. Evicting an internal Full node also evicts its Mamba data; evicting Mamba affects only Mamba; evicting a leaf removes everything on it. [D] https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/

### Hybrid / Gated DeltaNet / Mamba
- MambaRadixCache exists (now folded into Unified Radix Cache). Reason it is hard: SSM state updates in place, so it cannot be rolled back to a prefix; state is orders of magnitude larger than one token's KV; reuse is "all or nothing" (valid only at an exact prefix checkpoint). Match returns the deepest node that has a non-None Mamba state and whose key is a prefix of the input; the state is COPIED into a private slot for the new request. [D] PyTorch blog; LMSYS URC blog.
- Consequence: only prefixes that were checkpointed are reusable; a hit is not available at an arbitrary token boundary the way full-attention KV is. Checkpoint granularity/interval was not specified in the pages I read; the roadmap issue lists "store mamba state every k steps/branch point" as an open item and says current implementation supports page size = 1 only. [D for roadmap item; U for current interval] https://github.com/sgl-project/sglang/issues/12867 (may be stale)
- Strategies: `--mamba-radix-cache-strategy` V1 `no_buffer` (default, no overlap scheduler, lower memory) vs V2 `extra_buffer` (overlap scheduling; docs example `--page-size 64`, FLA kernel backend; higher memory). [D] https://lmsysorg.mintlify.app/cookbook/autoregressive/Qwen/Qwen3-Next (search snippet for default ratio 0.9 of `--mamba-full-memory-ratio` is from a search summary, [U] for exact default).
- Memory: hybrid models split memory into a request-level Mamba pool and a token-level KV pool, both fixed size; ratio set by `--mamba-full-memory-ratio`. Mamba state is allocated per request, so each running request pins one state slot. [D] PyTorch blog.
- Qwen3.8 (2.4T-A95B) is 3:1 GDN:full-attention, uses Unified Radix Cache with copy-on-write GDN state. [D] https://www.lmsys.org/blog/2026-08-12-qwen3-8-day0-support (2026-08-12). "Qwen 3.8 Flash Next" is not mentioned there; whether a smaller Flash/Next variant has the same cache behavior is [U], though [I] likely since same architecture family.
- Speculative decoding + radix cache: PyTorch blog's spec-decode benchmark launches with `--disable-radix-cache` [D, as of v0.5.5]; roadmap lists spec-decode compatibility with prefix cache as future work [D]. In vLLM, prefix caching + MTP on hybrid GDN models has open corruption bug reports [D that issues exist: https://github.com/vllm-project/vllm/issues/53912, /47194]. Design implication [I]: MTP and prefix reuse may be mutually exclusive on your nodes; test.

### Sessions
- `--enable-session-radix-cache` requires UnifiedRadixCache; client passes the same `session_id` on every request; the prompt must still contain full context (session id only labels cache references). Finished requests register their cache leaves under the session; `/close_session` ends it. [D] https://docs.sglang.io/docs/advanced_features/session_radix_cache
- "Soft protection, not memory pins": eviction order is unreferenced nodes first, then referenced nodes with fewer session references, then normal LRU. Referenced KV can still be evicted under pressure. No TTL/timeout documented. Supported-model list (hybrid?) not stated on the page. [D / U]
- Separate "streaming session" mode (`--enable-streaming-session`, PR #19171): per-session KV slots bypass radix matching after the first turn. [D from PR title/search summary] https://github.com/sgl-project/sglang/pull/19171
- Client must close sessions, including on error/cancel paths [D]; so a proxy that maps conversations to session ids must own close semantics.

### Scheduling, capacity, overload
- `--schedule-policy`: fcfs (default per server_arguments page), lpm, random, dfs-weight, lof, priority, routing-key. [D] server_arguments page. (An older tuning page and a search snippet say lpm is default; sources conflict; treat default as version dependent. [U])
- lpm reorders the waiting queue by longest prefix match; has scheduling overhead; best with heavy prefix sharing. [D] https://docs.sglang.io/advanced_features/hyperparameter_tuning.html
- `--max-running-requests` caps concurrent running requests, auto-derived from memory if unset. `--max-queued-requests` bounds the wait queue, unbounded if unset. [D]
- More requests than capacity: they wait in the scheduler queue (FIFO or policy-ordered). If the KV pool fills during decode, SGLang retracts running decode requests back to the queue; retracted requests recompute (or in PD/CPU-offload configurations restore from host). `--schedule-conservativeness` (default 1.0; ~1.3 if retractions frequent) reduces retraction; occasional "retract" warnings (about once per minute) are tolerable. Healthy queue in their guidance is 100-2000 pending (batch-serving mindset, not interactive). [D] hyperparameter tuning page; [D] retraction details from issues like #14972, #39645 (existence).
- Retraction on a hybrid model: whether the Mamba state is kept or recomputed was not found. [U]
- [I] For a node serving ~4 sessions, the radix cache, not slots, is what gets thrashed: 5th..Nth conversations evict the LRU conversation's checkpoint, and returning later means full re-prefill.

## 2. Routers

### SGLang Model Gateway (SMG, ex sglang-router)
- Policies: random, round_robin, power_of_two, cache_aware (default), bucket. [D] https://docs.sglang.io/docs/advanced_features/sgl_model_gateway
- cache_aware params, defaults as reported by search summary of the docs [D-ish; verify]: `--cache-threshold 0.3`, `--balance-abs-threshold 64`, `--balance-rel-threshold 1.5`, `--eviction-interval-secs 120`, `--max-tree-size 67108864`. https://github.com/sgl-project/sglang/blob/main/docs/advanced_features/sgl_model_gateway.md and https://pypi.org/project/sglang-router/ (param names confirmed there; default values not confirmed on fetched page).
- Algorithm (from the original design issue, may be out of date): if load is imbalanced, pick least loaded; else look up a per-worker radix tree of request TEXT (character prefixes, no tokenizer in the legacy path); if match ratio > threshold route to best match, else route to the worker with the smallest tree. [D] https://github.com/sgl-project/sglang/issues/7532
- Key property: the tree is an APPROXIMATION of what each worker caches. It is built from what the router sent, with no feedback from the worker about real evictions. Issue #7532 names unbounded growth/no TTL and "no feedback loop" as limitations (the later eviction interval + max tree size flags address growth). [D]
- Current SMG: below-threshold requests are routed by expected wait = (queued_tokens + dispatched_since_last_poll)/gen_throughput + kv_pressure; known bug: running requests invisible, stale throughput, burst piles on one worker (29:3). Affinity path has a "spill gate". [D] https://github.com/smg-project/smg/issues/2804
- Earlier load-balance bug: load only counted after response creation so fast decode / slow prefill collapsed onto one worker; fix tracks load before dispatch. [D] https://github.com/sgl-project/sglang/pull/27547
- Router has FIFO queue with 429 when full / 408 on queue timeout, retries with backoff, circuit breakers. [D] SMG docs.
- Hybrid-model awareness in the router: none found. The tree knows prefixes, not whether the worker kept a Mamba checkpoint at that depth. [U / I]

### vLLM / llm-d
- llm-d Router: approximate prefix scorer (in-memory LRU of prefix hashes, char-to-token ratio, "can diverge from actual model server state") vs precise scorer (vLLM KVEvents over ZMQ, global index of block->pod, token-exact). Claimed 57x faster TTFT / 2x throughput vs round-robin on 8 pods/16 H100 (vendor claim, workload specific). [D] https://llm-d.ai/docs/architecture/advanced/kv-management/prefix-cache-aware-routing ; https://llm-d.ai/blog/kvcache-wins-you-can-see
- llm-d router PR #2716: session-managed lookup built on KV events with session metadata; "ships no session producer": session identity, association policy and retention are external. Residency in memory, invalidated by eviction events and pod disconnects. [D] https://github.com/llm-d/llm-d-router/pull/2716 (open PR at time of reading, status [U]).
- vllm-project/router RFC #219: exact-match `session_id -> (worker_url, last_access_ms)` map, key from `x-session-id`/`x-user-id` or body, fallback to prefix match of serialized chat history, compile-time TTL; hit rate 20.5% -> 59.5% in their test. [D] https://github.com/vllm-project/router/issues/219 (RFC; implementation state [U]).
- vLLM hybrid prefix caching: modes "align" (experimental) and "all" for Qwen3.5/Qwen3-Next; block-granular GDN state save/restore (mamba chunk size 64). [D from PR titles] https://github.com/vllm-project/vllm/pull/36649 ; known MTP+prefix-cache corruption issues; ineffective-prefix-cache bug https://github.com/vllm-project/vllm/issues/51250. [D that issues exist]
- Whether llm-d's precise scorer understands hybrid-state validity: docs silent. [U]

## 3. General sticky-routing practice and anchors

- Envoy ring_hash/maglev `hash_balance_factor`: cap any host at factor/100 x average load (e.g. 150 -> 1.5x); typical 120-200; overflow spills to next host on the ring. Implements Mirrokni/Thorup/Zadimoghaddam bounded-load hashing. [D] https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/load_balancing_policies/common/v3/common.proto ; paper https://arxiv.org/abs/1608.01350
- HAProxy `hash-balance-factor` (needs `hash-type consistent`): >100, 0 disables, e.g. 150 -> no server above 1.5x average; Vimeo recommends 1.25-2. [D] https://www.haproxy.com/user-spotlight-series/haproxy-load-balancing-at-vimeo ; https://wohugb.gitbooks.io/haproxy/hash-balance-factor.html
- [I] With 5 nodes x 4 slots, "average load" is tiny integers (e.g. avg 2), so a 1.5x bound is 3 and granularity is coarse; ring hashing with 12 or so conversations gives lumpy placement. A stateful map (session -> node) with explicit spill is simpler and more controllable than hashing at this scale.
- OpenRouter: sticky provider routing after a cached request, only when cache reads are cheaper; 10 minutes of inactivity timer, reset by each successful request; falls back to next provider on error; keyed per account/model/conversation, `session_id` (<=256 chars) or `x-session-id` header overrides message-hash derivation. [D] https://openrouter.ai/docs/guides/best-practices/prompt-caching
- LiteLLM: `session_affinity` pre-call check pins a conversation to the deployment that served its first request (header such as `x-claude-code-session-id`); `prompt_caching` check keys on cacheable prefix. Affinity TTL was hardcoded to 5 min (issue #28427, breaks 1h cache), PR #40776 matches TTL to cache_control TTL. Session affinity disabled by default; docs say it is not needed for caching to work in most cases. [D] https://docs.litellm.ai/docs/auto_router/prompt_caching ; https://github.com/BerriAI/litellm/issues/28427 ; https://github.com/BerriAI/litellm/pull/40776
- Anthropic prompt caching: default TTL 5 minutes, 1-hour option (write 2x base, 5m write 1.25x, reads about 0.1x or lower); TTL refreshed at no cost on each hit; TTL measured from start of the request; 100% identical prefix needed; isolation per workspace/org; min cacheable 512-4096 tokens depending on model. [D] https://platform.claude.com/docs/en/build-with-claude/prompt-caching (fetched 2026-10-07). Third-party posts say default dropped from 1h to 5m on 2026-03-06 [unverified blog claim].
- OpenAI prompt caching: GPT-5.6+ TTL "30m" default, eligible for 30 minutes after last write or reuse; earlier models `in_memory` (about 5-10 min inactivity, up to 1h) or `24h`; routing by machine load plus hash of initial tokens plus optional `prompt_cache_key`; traffic above 15 requests/min per prefix/key can overflow to other machines and hurt hits; min 1,024 tokens. [D] https://developers.openai.com/api/docs/guides/prompt-caching (fetched 2026-10-07). Default 24h change on 2026-05-29 is from search snippet [unverified].
- Design anchors: hosted APIs cluster at 5-30 min idle windows (OpenRouter 10, Anthropic 5/60, OpenAI 30). All are refresh-on-use.

## 4. Affinity window length; costs of strict reservation

- No source found that prescribes a correct idle timeout for self-hosted affinity. [U] Closest: hosted TTLs above (design anchors) and "A Year in LLM Serving" (arXiv 2608.13573) which reports that prefixes are often evicted before later turns arrive, so affinity only pays when cache capacity is large enough for prefixes to stay resident. [D by search snippet; PDF not parseable, numbers unverified]
- CONCUR (arXiv 2601.22705): too many concurrent agents causes KV cache thrashing; admission control on active agents (AIMD-style on cache pressure) improves throughput. [D] https://arxiv.org/pdf/2601.22705
- Agent literature on tool pauses: paused agents' KV slots get LRU-evicted while other agents run, forcing full recompute on resume (AgentKV, arXiv 2609.14872; EfficientAgent 2609.33762). [D from search snippets; not read in full]
- Cache-aware vs balance tension: ICLR 2026 paper openreview R7fv5NWfMm, DualMap arXiv 2602.06502, CacheRoute arXiv 2608.19677 all argue fixed affinity overloads servers and blind balancing kills reuse; they use load-aware spill / periodic plans. [D from snippets]
- Hierarchical deadlock: found only an application-level example (pi-extensible-workflows issue #264): children collecting results can violate concurrency limits and leave the parent waiting forever for a permit; the rule there is nested children do not take their own slot because the parent already holds one. [D] https://github.com/vekexasia/pi-extensible-workflows/issues/264 . No inference-serving source on head-of-line blocking from per-session slot reservation; that is [I] from queueing theory: strict reservation turns idle sessions into dead capacity (a reserved-but-idle slot serves nobody) and a parent that holds a slot while awaiting children whose requests queue behind it can deadlock when slots are exhausted.
