## 1. What Codex 0.160.1 sends and requires

### Wire protocol
- D: `wire_api = "chat"` is a hard config error: `codex-rs/model-provider-info/src/lib.rs:100` "`wire_api = \"chat\"` is no longer supported". Only `WireApi::Responses` exists. Deprecation announced 2025-12-09, removal early Feb 2026 (https://github.com/openai/codex/discussions/7782; PR #10157 per a search summary, U). `ollama-chat` provider also removed (lib.rs:102). So for Codex there is no chat-completions fallback; a custom provider MUST serve `/v1/responses`.
- D: `ModelProviderInfo` defaults (lib.rs:66-75): `stream_idle_timeout_ms` 300000, `stream_max_retries` 5, `request_max_retries` 4, caps 100 each, `websocket_connect_timeout_ms` 15000. `supports_websockets` is true only for the built-in OpenAI provider (lib.rs:561); a custom provider has it false (lib.rs:601, :775). I: so a custom provider uses plain HTTP POST + SSE.
- D (spike C, raw bodies): HTTP `POST /v1/responses`, `accept: text/event-stream`, `content-type: application/json`, 39 KB body at turn 1 growing by about 340 B per tool loop.

### Request body (observed, Codex 0.160.1, spike C run codex-s1-plain)
`model, instructions (16979 chars), input[list], tools[9], tool_choice:"auto", parallel_tool_calls:true, reasoning:{summary:"auto"}, store:false, stream:true, include:["reasoning.encrypted_content"], prompt_cache_key:<session id>, client_metadata:{x-codex-turn-metadata, x-codex-window-id, session_id, thread_id, x-codex-installation-id, root_turn_id, turn_id}`.
- D: serde field order puts routing fields first (`model`, `stream`, ..., `input`) "gateways may inspect request bodies incrementally" (`codex-api/src/common.rs:280`).
- D (observed): `previous_response_id` was absent in all 22 Codex requests recorded. `store` is false. Each turn re-sends the full history (`input` grows by `function_call` + `function_call_output` pairs). Item ids are client-made: `fc_2`, `fco_<uuid>`, `msg_<uuid>`; call ids `call_N`.
- D (source): `previous_response_id` is only built on the WEBSOCKET path (`core/src/client.rs:2013-2032`, `codex-api/src/endpoint/responses_websocket.rs`). Websocket is only for the OpenAI provider. I: with a custom HTTP provider Codex 0.160.1 never sends `previous_response_id`. U: not tested against an engine that returns real `resp_` ids, or with a ChatGPT-auth provider.
- Tool types seen in `tools`: `function` (exec_command, write_stdin, request_user_input, view_image, get_goal, create_goal, update_goal), `namespace` (multi_agent_v1), `web_search`. D: Codex also has `custom` (freeform, e.g. apply_patch) and `CustomToolCall` items (`protocol/src/models.rs:1136`); the fake run did not exercise them. U.
- D (source): zstd request compression exists, but only when the provider is OpenAI and auth is the Codex backend (`client.rs:1632`, feature `EnableRequestCompression`). Not used for custom providers. (Ollama still handles `Content-Encoding: zstd`, `server/responses_compact.go:72`, so a proxy that reads bodies should tolerate it, I.)
- D: Codex calls `/v1/responses/compact` ("remote_compaction_v2" beta header `x-codex-beta-features: remote_compaction_v2` was sent in spike). Ollama and mlx-vlm implement `/responses/compact`; llama.cpp does not (U; only `/v1/responses/input_tokens` seen). Issue https://github.com/openai/codex/issues/45393 (0.154.0): after compaction, resume against a third-party provider fails with `input.12: item type "compaction" is not supported`.

### Headers (observed, spike C)
`session-id`, `thread-id` (both equal the session id; per-conversation), `x-client-request-id` (= session id, not per request), `x-codex-window-id` (`<session id>:<window number>`), `x-codex-turn-metadata` (JSON: session_id, thread_id, turn_id, window_id, agent_name `/root`, request_kind, thread_source ...), `x-codex-beta-features`, `originator: codex_exec`, `user-agent: codex_exec/0.160.1 ...`, `authorization: Bearer`. D (source) also `x-codex-parent-thread-id` (subagent), `x-codex-installation-id`. Body `prompt_cache_key` = session id and `client_metadata.session_id` repeat the id. Resume keeps the id (run codex-s6-resume). Distinct sessions give distinct ids (3 sessions, 3 ids). U: subagent ids (multi_agent_v1) and compaction not captured.

### SSE events Codex consumes (D, `codex-api/src/sse/responses.rs:344-495`)
Acts on: `response.created` (reads `response.id`), `response.output_item.added`, `response.output_item.done` (the ONLY place Codex builds the finished item: messages, function_call, reasoning), `response.output_text.delta`, `response.reasoning_summary_text.delta/.done`, `response.reasoning_text.delta`, `response.reasoning_summary_part.added`, `response.custom_tool_call_input.delta`, `response.completed` / `response.incomplete` (reads `usage`: `input_tokens_details.cached_tokens`, `cache_write_tokens`, `output_tokens_details.reasoning_tokens`), `response.failed`, `error`. Ignored (trace only): `response.in_progress`, `response.metadata`, `response.output_text.done`, `response.reasoning_summary_part.done`, and ANY `*.delta` not listed, including `response.function_call_arguments.delta`. I: an engine that streams a tool call without a correct `output_item.done` carrying full `arguments` breaks Codex even if the deltas are right.
- Stream ends without `response.completed` -> `stream closed before response.completed` (retry). `response.incomplete` with reason `content_filter` -> error. Idle 300 s with no SSE event -> `idle timeout waiting for SSE`.
- `response.failed` error codes Codex maps (`responses_error.rs:47`): `context_length_exceeded` (fatal, triggers compaction path), `insufficient_quota` and spend-limit codes (fatal), `usage_not_included`, policy codes; unknown code -> retryable stream error; `error.headers` can carry retry-after.
- D (OpenAI docs, thin): event list `response.created`, `response.in_progress`, `response.output_item.added`, `response.content_part.added`, `response.output_text.delta`, `response.function_call_arguments.delta`, `response.completed`, `error` (https://developers.openai.com/api/docs/guides/streaming-responses). The page does not define `sequence_number` or the error event shape. U: full ordering and error shapes from OpenAI's API reference were not read; the order above comes from the engines' source (created, in_progress, output_item.added, content_part.added, deltas, *.done, output_item.done, completed).

### Retry and hold behaviour (spike D, Codex 0.160.1, fake server)
- Hold (send no byte) up to 600 s: Codex never gave up (T=60..600 ok). Not Codex-limited at all in no-byte state (D observed).
- 200 head then nothing: gives up at 300 s (`idle timeout`). SSE comment `: keep-alive`: does NOT reset the idle timer (fails at 300 s). `event: ping` as a real SSE event: resets (400 s ok). I: `: ping` comments pass through the proxy but do not keep Codex alive; if early headers are ever used, send a data event.
- Retries: 503/502/504/500/529: 30 requests over 117-121 s (D observed; I: 6 stream attempts x 5 request attempts, from defaults 5 and 4 in source). 429: Codex fails at once (`exceeded retry limit`). 408 and 409 retried. `Retry-After` honoured on 503/529 (30 s and 120 s waited), not on 429. 400 not retried. Drop at 5 s: 30 requests. Error event after 25 s: 5 reconnects then fail.
- Hold 250 s then 503/504/529/408 -> completes after retry; hold 250 s then 429 -> FAILS.
- Related D: issue https://github.com/openai/codex/issues/24973: `response.failed` with `error:null` plus a top-level `error` object shows as `stream disconnected before completion` (U whether Codex or provider is at fault).

## 3. Proxy implications

### Affinity
- D: use `session-id` (or `thread-id`) header first; body `prompt_cache_key` and `client_metadata.session_id` are the same value. Fallback derived key must handle `instructions` + the first real `input` message after `<environment_context>` (keyv1 in sC does this; K1 collides across all Codex sessions in one directory).
- The proxy can read the headers without touching the body. Do not parse the body unless needed. If it must, tolerate `Content-Encoding: zstd` (not sent to custom providers by Codex 0.160.1, I).
- `x-codex-window-id` changes with context window (`:N`). Do NOT key on it (I): compaction bumps window number; the cache after compaction is cold anyway but the conversation identity is the same. U: not captured on compaction.
- Subagents: `x-codex-parent-thread-id` and own `thread-id` (D source, not captured). Key = thread-id so children get their own node choice; U.
- `previous_response_id`: Codex over HTTP does not send it (D+observed). If a client (non-Codex) does, and the engine is stateful (vLLM with store, SGLang with store, LM Studio, LocalAI, mlx-vlm), the id is meaningful only on the node that made it. Proxy rule options: (a) record `response.id` seen in the stream (`response.created`/`completed`) in the affinity table, mapping id -> node, and route a follow-up there; (b) reject. Option (a) costs a stream parse; inspecting only the first events is cheap. If the engine is stateless (llama-server rejects with 400; Ollama silently ignores, which is the dangerous case: context loss with no error) the proxy should refuse or strip nothing: pass through and let it fail only if the engine fails loudly; for Ollama it is a silent hazard to record. All I, no test.
- Restart of the proxy: id->node map is lost; a stateful follow-up returns 404 from the wrong node. Same cost class as cold turns.

### Hold
- Codex tolerates a no-byte hold up to at least 600 s (D observed), the longest of all clients tested. Default must stay "send nothing". Early headers are harmful with Codex unless a real data event (not a comment) is sent at least every 300 s.
- Hold-limit error: 503 with `Retry-After` is the only status Codex retries with a delay AND honours (30 and 120 s worked). 429 is fatal for Codex. 408/409 are retried without delay. A 503 costs up to 30 requests / 120 s if every attempt fails.
- Error after the 200 head: send `response.failed` with `error.code` (not `error:null`), and prefer a fresh status code before the head.

### Must not change
- Item ids (`fc_*`, `fco_*`, `msg_*`, `rs_*`, `call_*`): Codex makes them and replays them; engines (llama.cpp) mint their own on output. D: Codex's `prepare_response_items_for_request` rewrites ids (`client.rs:2037`). I: a proxy that rewrites ids breaks nothing only if it rewrites consistently; safest is byte pass-through.
- `reasoning.encrypted_content` / `include`: Codex asks for it; engines mostly ignore or emit own blobs (SGLang's is reversible encoding, mlx-vlm own capsule). A proxy must not drop `include` or strip `encrypted_content`. If one conversation moves between nodes of different engines, a replayed foreign blob is ignored or rejected by the second engine (U).
- `store`, `instructions`, `prompt_cache_key`, field order: pass the body byte for byte (also required by VIS-007).
- Tool list per request: engine behaviour on `namespace`/`web_search` differs (drop vs flatten). Do not "fix" it in the proxy.

### Translation temptation
- Why engines translate: three of the engines (llama.cpp, Ollama, probably LocalAI) already convert Responses to chat completions internally. Their known defects (table above) are all translation defects: reasoning items, non-function tools, custom tools, developer role, ordering, `sequence_number`, previous id.
- Open-source Responses-to-chat adapters exist (D, repos found by search, not run): https://github.com/MetaFARS/codex-relay (Rust; handles streaming, parallel tool calls, reasoning_content, `previous_response_id` via its own session store with TTL and max sessions, `--tool-denylist`, provider workarounds), https://github.com/xeonvs/responses-proxy (SSE and websocket), https://github.com/NoahStepheno/completion-to-response, https://github.com/codeproxy-ai/cli, https://github.com/scorpioash/codex-openai-proxy, https://github.com/DevvGwardo/codex-minimax-proxy. LiteLLM also bridges (repo cloned earlier, https://github.com/BerriAI/litellm). Known problems in their own words: session state for `previous_response_id` and reasoning (a stateful translator needs the same affinity problem), tools with no chat equivalent (denylist), version mismatch silent failures (`spawn_agent`), per-provider quirks (GLM, DeepSeek DSML).
- I: translation would put Legatus in the business of maintaining a moving target (Codex adds item types monthly: `compaction`, `additional_tools`, `namespace`, `tool_search`; open issues #45393, #44710). Legatus v1 principle "does not change the bytes". It would also own the cache-key question: after translation the engine sees chat messages that no longer match its own cache layout between engine versions.
- I: translation is acceptable only as a separate, opt-in, per-route component, never default, with a fixture-tested item-type table.

### Decision to record for the owner
1. Accept `/v1/responses` as a pass-through route (replaces DEC-057 404), engines declared in the registry with a `responses` capability flag, default false; the proxy answers 404 or a protocol error for a route whose pool has no `responses` node.
2. Affinity key for Responses: `session-id` -> `thread-id` -> body `prompt_cache_key` -> keyv1 derived key. Never `x-codex-window-id`.
3. Record `response.id` -> node for engines flagged `stateful_responses`; refuse (or warn) on `previous_response_id` for engines flagged `ignores_previous_response_id` (Ollama today).
4. No translation in v1. mlx_lm.server nodes cannot serve Codex; owner choice: use mlx-vlm, or defer.
5. Hold config for the `responses` protocol: hold no byte; error with 503 + `Retry-After`; never 429.
6. Required real-engine test before claiming support: a Codex 0.160.1 session against llama-server, Ollama, vLLM, gufo with real tool loops (apply_patch/custom tool, reasoning items, compaction). Spike C/D used a fake server only.

### 5.2 SSE parser and error handling (`codex-api/src/sse/responses.rs`, `core/src/session/turn.rs`)
- Reads `event`-less framing: it parses `data:` JSON and switches on the JSON `type` field, not on the SSE `event:` line (`process_responses_event`, :344). A data-less `event: ping` line or a comment does not parse as an event. Spike D: `event: ping` (a real SSE event) reset the idle timer; `: keep-alive` comment did not. I: the eventsource layer yields an event for `event: ping` and the loop resets `timeout(idle_timeout, stream.next())`; JSON parse failure just logs and continues (`:577`). So ANY complete SSE event, even unparseable, resets the 300 s timer.
- Acts on: `response.created` (needs `response.id`), `response.output_item.added`, `response.output_item.done` (item parsed into `ResponseItem`; unparseable item is dropped with a debug log, not an error), `response.output_text.delta`, `response.custom_tool_call_input.delta`, `response.reasoning_summary_text.delta/.done`, `response.reasoning_text.delta`, `response.reasoning_summary_part.added`, `response.completed`, `response.incomplete`, `response.failed`, `error`.
- Ignores (trace): `response.in_progress`, `response.metadata`, `response.output_text.done`, `response.reasoning_summary_part.done`, `responsesapi.websocket_timing`, any other `*.delta` (so `response.function_call_arguments.delta` is ignored), and any unknown type (debug log). Unknown events never fail the stream.
- Tool calls and messages are taken ONLY from `output_item.done` items. Streaming text for display comes from `output_text.delta`.
- `response.completed`: reads `response.id`, `usage.input_tokens`, `usage.input_tokens_details.cached_tokens` (and `cache_write_tokens`), `usage.output_tokens`, `usage.output_tokens_details.reasoning_tokens`, `total_tokens`; all tolerate `null` (Codex's own fixture sends null details). Missing `usage` is allowed (`token_usage: None`). `response.incomplete` is treated as completion with `interrupted`; reason `content_filter` is an error.
- `response.failed`: `parse_failed_response` (`responses_error.rs:26`) reads `response.error` `{code,message}`; `context_length_exceeded`, quota codes, `usage_not_included`, policy codes are terminal, special-cased; unknown or null error -> `ApiError::Stream("response.failed event received")` (retryable stream error) or `Retryable` when `error.headers` has retry-after. `error` event: only flex-unavailable shape is special-cased; otherwise falls through to the "unhandled" branch (no failure by itself); the stream then ends -> `stream closed before response.completed`.
- Stream end: connection closed before `response.completed` -> `ApiError::Stream("stream closed before response.completed")`; no event for `stream_idle_timeout` (default 300000 ms, `lib.rs:63`) -> `idle timeout waiting for SSE`. Both go to the turn-level reconnect loop: `stream_max_retries` default 5 (`:64`, cap 100). Core test `core/tests/suite/stream_no_completed.rs` asserts the retry on early close.
- HTTP-level retry (`codex-client/src/retry.rs`): `RetryOn{retry_429, retry_5xx, retry_transport}`; provider `retry_429: false` (`lib.rs:451`) so 429 is never retried; any 5xx (`status.is_server_error()`) and timeout/connect errors are retried; `request_max_retries` default 4 (`:65`), exponential backoff with +-10% jitter from a base delay. 408, 409 are not in `RetryOn`; the spike saw them retried, so I: another layer (turn-level reconnect) handles them. 30 requests = 6 x 5 (I).
- Server response header `x-codex-turn-state` (`sse/responses.rs:68,283`) is stored per turn and sent back on later requests of the same turn (`client.rs:2328`). Only OpenAI's backend sets it; a local engine will not. A proxy must pass this header both ways unchanged (I).

### 5.5 Minimum a server must implement to run Codex tasks (checklist)
Derived from the parser and from Codex's own fixtures (D) and from the spike runs (observed with a fake server, all of 1-6 sufficient for a 4-step tool loop).
1. `POST {base_url}/responses` (base_url ends in `/v1`), accept JSON body of 20 to 40+ KB, ignore unknown fields (`client_metadata`, `include`, `prompt_cache_key`, `service_tier`, `text`, `access_programs`, `stream_options`), accept `Authorization: Bearer`. `store:false` must not fail.
2. Accept `input` items: `message` with roles developer, user, assistant (content parts `input_text`, `output_text`, `input_image`), `reasoning` (including `summary:null`, `content` absent, `encrypted_content` present), `function_call` and `function_call_output`; ideally `custom_tool_call` and `custom_tool_call_output`; must not reject `compaction` items if the conversation was compacted (issue #45393). Accept `tools` of type `function` (required), and tolerate `namespace`, `web_search`, `custom` entries (drop or flatten, do not 400).
3. Reply `200` with `content-type: text/event-stream`. Each event is `data: {json}` with a `type` field; `event:` lines are optional for Codex.
4. Per turn emit, in order: `response.created` with `response.id`; for each output item a `response.output_item.done` with the FULL item (`message` with `content:[{type:"output_text",text}]`, or `function_call` with `call_id`, `name`, `arguments` as a JSON string, or `reasoning` with `summary[]`); optional `response.output_text.delta` before the message `done`; finally `response.completed` with `response.id` (usage optional; if given, `input_tokens`, `input_tokens_details.cached_tokens`, `output_tokens`, `output_tokens_details.reasoning_tokens`, `total_tokens`, nulls allowed).
5. Close the stream after `response.completed`. A close before it causes up to 5 reconnects.
6. Errors: HTTP 503/5xx before the head (retried, `Retry-After` honoured on 503/529); never 429 (fatal for Codex); mid-stream failure as `response.failed` with `response.error.code` and `message`; `context_length_exceeded` as that exact code so Codex compacts.
7. Function calls must be well formed: `call_id` unique per call; `arguments` valid JSON string; `parallel_tool_calls:true` means several `function_call` items in one response must be allowed. The next request carries `function_call` + `function_call_output` with the same `call_id`.
8. Reasoning: emit a `reasoning` item whose `summary` is an array (empty is fine) if the model reasons; Codex replays it in later `input`. The server must accept it back. `encrypted_content` may be absent or opaque; the server need not decrypt it.
9. Idle safety: send an SSE event at least every 300 s while generating, otherwise Codex disconnects. A comment line does not count (spike D).
10. Optional but useful: `GET /v1/models` (for `--oss` probes; LM Studio helper calls `GET {base}/models`), `POST /v1/responses/compact` (remote compaction beta), `x-codex-turn-state` passthrough (only OpenAI sets it).
Not required (D): `sequence_number`, `response.in_progress`, `output_item.added`, `content_part.*`, `function_call_arguments.delta`, `previous_response_id` support (HTTP path), `usage`, server-side state.
Consequence for engines (I): llama-server today fails item 2 (reasoning with `summary:null`, `custom_tool_call`) and drops non-function tools (item 2 tolerance), so it is NOT yet a drop-in for 0.160.1 without open PRs #27751 / #29159 fixes; Ollama silently drops developer items (#18305, open); gufo documents an explicit Codex-compatible subset (D docs, U run).
